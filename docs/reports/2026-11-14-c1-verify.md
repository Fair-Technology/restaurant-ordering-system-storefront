## Part 2 — rs-admin order board labels (read-only; rs-admin NOT changed)

`git status` in `rs-admin` is clean; nothing was edited.

### Finding: the expected defect does not exist

The claim was that `src/components/orders/{OrderDetail,OrderCard,UpcomingOrders}.tsx` render
``t(`orders.rejectReason.${reason}`)`` and that `payment_unavailable` (plus `no_response` / `payment_failed`)
therefore shows as a raw key. **That is not what the code does.** In all three files, `reason` iterates the
fixed staff list `REJECT_REASONS` (`src/features/orders/intake.ts:3`):

```
REJECT_REASONS = ['too_busy', 'item_unavailable', 'closing_soon', 'other']
```

- `OrderCard.tsx:246-256` — reason chips built from `REJECT_REASONS`
- `UpcomingOrders.tsx:97-107` — reason chips built from `REJECT_REASONS`
- `OrderDetail.tsx:360-364` — reason chips built from `REJECT_REASONS`

All four keys exist in **both** `public/locales/{en,de}/common.json` (`orders.rejectReason.*`). So every
`orders.rejectReason.*` lookup the app performs resolves to a label — there is no fallback to a raw key.

More importantly, **no rs-admin component renders an order's stored `rejectionReason` at all.**
`grep -rn rejectionReason rs-admin/src` returns exactly one hit — the generated type
`src/services/api.ts:1892` — and no reader. The board (`OrdersPage`), the history list
(`OrderHistoryList`) and the detail panel show the order *state* badge and payment status, never the decline
reason. So staff never see `orders.rejectReason.payment_unavailable`, because nothing displays a backend
rejection reason.

**Correction needed:** finding **B** in `docs/reports/2026-11-13-c1.md` ("staff see
`orders.rejectReason.payment_unavailable`") is inaccurate and should be dropped/corrected. There is no
user-visible label defect; the only real, latent issue is that the stored reason is not surfaced in the UI
which is a *feature gap*, not a broken label.

### Latent risk (not a current bug)
`ordersApi.ts` / generated `api.ts` `RejectReason` is stale — it omits `payment_unavailable`. If a future
change *starts* rendering an order's `rejectionReason` via `t('orders.rejectReason.'+reason)`, then
`payment_unavailable`, `no_response`, `payment_failed` and `shop_unavailable` would fall back to the raw key,
because those entries are absent from both locale files. The forcing function already exists
(`src/i18n/locales.test.ts:69` asserts a key per `REJECT_REASONS` entry) but only covers the four staff
reasons today. Recommendation: if the reason is ever surfaced to staff, add the missing `rejectReason`
entries to both locales **and** extend `REJECT_REASONS`/the union.

### Accept button on a held `PLACED` order
A held `PLACED` order **does** show an Accept button (row button "Accept", and the detail panel's
`Accept · ready in 20 min`). With `POST /shops/<id>/orders/<id>/accept` returning `409
{"error":"PAYMENT_CONFIG_UNAVAILABLE_ERROR"}`, the UI shows only the **generic** toast:

> That didn't work — the order may have changed. The list has been refreshed.  (`orders.actionFailed`)

The code `PAYMENT_CONFIG_UNAVAILABLE_ERROR` is not shown and `grep -rn PAYMENT_CONFIG_UNAVAILABLE rs-admin/src`
finds **nothing** — the admin has no special handling for a platform-caused capture failure
(`OrderCard.accept` / `useOrderActions.track` catch every error into that one message). This matches the note
in C1 finding C. Screenshot → `docs/reports/evidence/admin-accept-config-failure.png`.
