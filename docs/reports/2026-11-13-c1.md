# C1 — diner copy for platform-caused payment failure

## B2 contract (read from rs-backend commit 3e12d7d, read-only)
- **There is no new order state.** The order stays `PLACED`, with `captureConfigFailure {at, attempts}` set on the stored order. The accept timer retries each minute.
- At `autoRejectAt` it goes `REJECTED` with the new reason **`payment_unavailable`** (instead of `no_response`), and is not counted against the shop's auto-pause.
- Backend already has EN/DE email text for `payment_unavailable` (`emailTemplates.ts` ~line 53).
- `captureConfigFailure` is **not** in the customer order DTO (`toCustomerOrderDto.ts` only whitelists the new reason), so the diner page cannot tell a held-PLACED order from a normal one.

## Changed
- `src/utils/orderCopy.ts`: `rejectReason.payment_unavailable` in `en` and `de`. It says technical problem, not your card and not the restaurant, not charged, reservation released. It differs from `payment_failed` (card/decline wording, unchanged).
- `src/api/orderEndpoints.ts`, `src/api/endpoints.ts`: `RejectReason` union gains `payment_unavailable`. `Record<RejectReason,string>` in both copy maps enforces i18n key parity.
- Tests: `npm run check` and `npm run build` pass. No unit/UI test exercises this; not rendered in a browser (unverified visually).
