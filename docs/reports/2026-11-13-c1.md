## B2 contract (read from rs-backend `main` @ 76fc490, read-only)
- **There is no new order state.** The order stays `PLACED` with `captureConfigFailure {at, attempts}` on the stored order; the accept timer retries each minute.
- At `autoRejectAt` it goes `REJECTED` with the new reason **`payment_unavailable`** (not `no_response`), and is not counted against the shop's auto-pause.
- `payment_unavailable` is present in the backend contract: `domain/order/Order.ts:50`, `toCustomerOrderDto.ts:10` (KNOWN_REASONS), `timers/executeProcessOrderTimers.ts:155`, `src/swagger/swagger.json:9447`, and diner-facing email copy in `notifications/emailTemplates.ts:52` (EN + DE).
- `captureConfigFailure` is **not** in the customer order DTO — `toCustomerOrderDto.ts` only whitelists the new *reason*. So the diner page cannot tell a held-`PLACED` order from a normal one.

## Not verified / gaps
1. **Not rendered in a browser.** The copy is type-checked and wired to the render path, but no page was loaded against a `payment_unavailable` order. `npm test` (Playwright) was not run — no existing spec covers this reason.
2. **The brief's *wait-state* wording ("technical problem, your card is only held") is not implementable here.** While the order sits `PLACED` and capture is being retried, the customer DTO carries no signal, so there is nothing for the diner page to branch on. Needs a backend change exposing a flag (e.g. `paymentHeld`) on the customer DTO; then add a `statusPlacedHeld` string. Suggested EN: "We have a technical problem finishing your payment. Your card is only on hold — you have not been charged. We keep retrying; you don't need to do anything." DE: "Beim Abschluss Ihrer Zahlung gibt es ein technisches Problem. Ihre Karte ist nur reserviert — es wurde nichts abgebucht. Wir versuchen es weiter, Sie müssen nichts tun."
3. **Emails live in rs-backend, not editable from this packet** ("this repo only" boundary). See finding A below.

Pre-existing for the older reasons; `payment_unavailable` extends it.
