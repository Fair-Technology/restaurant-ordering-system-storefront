# C3 — Browser checks on the diner-facing storefront slices

Packet C3 · owner `frontend-engineer-1` · repo `rs-storefront` · measured 2026-11-14.

**Verdict: no defect found in any slice I could reach. Four of the six items are verified live against the
dev API; two are partly verified, with the unverified half named below. One unintended write to the shared
dev database happened — disclosed under D1. No source file was changed.**

## How it was run

- **Dev API.** The `rs-backend` checkout (`main`) was built (`npm run build`) and served locally with Azure
  Functions Core Tools: `func start --port 7071`. It uses `rs-backend/local.settings.json`, i.e. the dev
  Cosmos account and the Stripe **test** keys; the timers are disabled by that file. Names only, no values.
  This is the only usable dev API for a local frontend: the deployed dev Function App
  (`restaurant-ordering-system-dev.azurewebsites.net`) returns **no CORS headers** for
  `Origin: http://localhost:5176` (preflight `OPTIONS` → `204` with no `Access-Control-Allow-Origin`), so a
  browser page served from localhost cannot call it. The local host sets
  `Access-Control-Allow-Origin: http://localhost:5176` from `Host.CORS` in the same file.
- **Storefront.** This worktree, `npm run dev -- --port 5176 --strictPort`, pointed at
  `http://localhost:7071/api` (the default in `vite.config.ts` / `src/api/baseApi.ts`).
- **Seeded restaurant.** Ma Pasta, slug `mapasta`, shop `eeefdd4a-0ceb-4ae3-84de-0091bddfcf7d`.
  Note the app calls `GET /shops/slug/{slug}` (anonymous), not `GET /shops/{slug}` (403).
- **Browser.** Chromium, driven live against the running app; German copy read from the very module the app
  serves in the running page (`await import('/src/utils/orderCopy.ts')`), so what is quoted is the shipped
  string, not a copy in this report.
- **Storefront test suite (mocked API).** `npx playwright test` → **207 passed (32.9 s)**.

## Results

### 1. 8b — "On its way" diner page — NOT REPRODUCIBLE LIVE. "ist unterwegs" email — VERIFIED IN SOURCE (not sent)

The diner order page (`/shops/:slug/orders/:orderId?t=<token>`) needs a real order id **and** its access
token; both come from a paid order. Creating one is out of bounds here (it writes an order to the shared dev
Cosmos and emails the diner), and no order credential was available. So the page was not rendered live.

What was verified:

- The shipped copy, read from the running app: `statusOutForDelivery` = **"On its way to you"** / **"Unterwegs
  zu Ihnen"**; `stepOnTheWay` = "On the way" / **"Unterwegs"**.
- The render path: `src/features/order/CustomerOrderPage.tsx:196` sets the title to `copy.statusOutForDelivery`
  for the out-for-delivery state, and line 65 uses `copy.stepOnTheWay` for the step rail.
- The repo's own test `tests/specs/card-order.spec.ts` → "the diner order page shows delivery" mocks a
  `OUT_FOR_DELIVERY` delivery order and asserts "On its way to you" is visible. It is green in the 207-test
  run above. That is a mocked render, not the dev API.
- **The email is not sent by this repo.** It lives in `rs-backend`
  (`src/application/order/notifications/emailTemplates.ts`): subject kind `order_out_for_delivery` is
  `"{name}: Bestellung {ref} ist unterwegs"` / `"{name}: order {ref} is on its way"` (line 233), and the body
  line is **"Ihre Bestellung ist unterwegs zu Ihnen."** / "Your order is on its way." (line 263). Read only —
  no email was sent, and nothing here proves the send path fires.

### 2. Combo display and selection — PASSED LIVE. VAT-per-component split — NOT SHOWN HERE

Live against the dev API, on `Menu deals` / `Menüs`:

  "Lasagne meal €19.90".

**VAT-per-component split: the storefront does not display one anywhere.** The only VAT text is
`inclVat` — "incl. VAT" / "inkl. MwSt." — next to a single total (`CheckoutPage` summary "Total incl. VAT",

single **`taxCents: 139`** on `subtotalCents: 1490` — one aggregate figure, no per-line or per-rate split
(`BasketQuoteDto` has one `taxCents`). Per-component tax data does exist further along: the order DTO carries

are right for a real combo **cannot be checked without an order**, so it is reported unverified.

### 3. Discount code at checkout, and the German "Rabatt" wording — PASSED LIVE

- The checkout summary shows **"Have a discount code?"**; opening it reveals an input labelled "Discount code"
  and an "Apply" button.
- Typing `NOPE123` and applying **did re-ask the server**: a second `POST /orders/quote` fired (network
  entries 1 → 2, and captured in-page), the box locked to the applied code with a **"Remove"** button, and the
  message **"This code is not valid."** appeared. "Continue to payment" went disabled while the code was
  rejected. That is the correct path for an unknown code — the wording comes from the server's
  `discountProblem: 'unknown'`, not from a client-side guess.
- German wording, read from the shipped copy module in the running app:

  | key | de | en |
  |---|---|---|
  | `haveCode` | **Rabattcode?** | Have a discount code? |
  | `codeLabel` | **Rabattcode** | Discount code |
  | `discountLine` | **Rabatt (CODE)** | Discount (CODE) |
  | `discountChanged` | Ihr Rabatt hat sich geändert … | Your discount has changed … |
  | `codeUnknown` | Dieser Code ist ungültig. | This code is not valid. |
  | `codeAlreadyUsed` | Sie haben diesen Code bereits eingelöst. | You have already used this code. |
  | `loyaltyOptIn` | … einen **Gutschein** über … | … a voucher worth … |

  **"Rabatt" is the right word for a price discount, and "Gutschein" is used only for the loyalty voucher**,
  which is correct German usage. No wrong wording found.

### 6. 8d loyalty path — no extra personal data — PARTLY VERIFIED

- **Live:** the loyalty opt-in box is **not rendered on the seeded shop**. The live quote for Ma Pasta returns
  `"loyalty": null`, and `CheckoutPage` only renders the checkbox when `quote.loyalty` is set. So this shop
  cannot exercise the diner-side loyalty path at all.
- **The payload, from the code that builds it** (`src/features/checkout/CheckoutPage.tsx:249-269`): the
  place-order body is the quote argument (`shopId`, `items`, `language`, `fulfilmentMode`, optional
  `postcode` / `scheduledFor` / `discountCode`) plus `customerName`, `customerEmail`, `customerPhone`,
  `customerNotes`, `customerAddress`, optional `deliveryAddress` / `expectedDeliveryFeeCents`, the optional
  discount echo, `paymentMethod`, `idempotencyKey`, `legalRevisions` and the two `replaces*` fields.
  **The only loyalty field is `loyaltyOptIn: true`**, added on line 261 and only when the box is ticked;
  nothing else is added for loyalty. The quote request carries no customer fields at all.
- **The repo's own test pins it**: `tests/specs/card-order.spec.ts` → "the loyalty offer can be ticked and is
  sent" captures the real `POST /orders` body and asserts `loyaltyOptIn: true` when ticked, and asserts the
  key is **absent** when it is not. Green in the 207-test run.
- **Backend side, read only** (`rs-backend`): the request DTO adds only the boolean
  (`src/application/order/checkout/dtos.ts:29`); `executeCheckout.ts` stores `loyaltyOptIn: true` only when
  the shop actually runs the offer (line 371, 424), and `issueLoyaltyVoucher.ts` reuses
  **`order.customerEmail`** — an address the order already carries — rather than collecting anything new.
  What the voucher email ultimately contains was not observed.

## Unverified — stated plainly

- **The "ist unterwegs" email was never sent.** It is `rs-backend` code, read only; nothing here proves the

- A `GET`/`POST` returning 200 is not proof of a write: the quote and shop calls above are reads, and I did
  not confirm anything the backend stored.

## Findings and disclosures

**D1 — an unintended write to the shared dev database, disclosed.** Item 6 was meant to capture the real
`POST /orders` body from the browser by hooking `window.fetch` and rejecting the request before it left the
page. The hook did not catch RTK Query's fetch, so the request went through: the checkout advanced to the
payment step, i.e. the API answered with a card-checkout result. Per the e2e repo's own notes that means one
`checkout_sessions` document in the shared dev Cosmos and one Stripe **test-mode** PaymentIntent — **no order
and no email** are created (the diner never pays, and `reconcileCheckouts` handles the abandoned session).
The intended capture was not obtained; only "a response came back" is known. The submit was not repeated.

**F1 — a code the shop does not use is validated server-side, not guessed.** Worth recording because it is
the behaviour the packet asked about: applying a code always re-quotes, so a **valid** code is priced by the
server and an invalid one shows the server's reason. No change needed.

**No source defect was found in any slice of this repo that I could reach, so this PR carries the report
only — no code change.**
